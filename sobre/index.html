O projeto

Quem chega à UnB tropeça em siglas e apelidos: DEG, BCE, FCTE, "menção SR", "trancamento geral". A explicação costuma estar espalhada em sites e documentos diferentes e, muitas vezes, usa mais jargão para explicar o jargão.

“O objetivo do produto é auxiliar estudantes da UnB, especialmente calouros, a compreender siglas e termos exclusivos da universidade, oferecendo consultas rápidas e confiáveis, para reduzir a confusão e o tempo perdido navegando por documentos e sistemas institucionais.”

Objetivo do produto, definido pela equipe no Figma

O projeto é inspirado no glossario-ufcg, da Universidade Federal de Campina Grande. Ele nasce na disciplina Métodos de Desenvolvimento de Software (MDS) da UnB, onde o foco é tanto o produto quanto a qualidade do processo de desenvolvimento.

São duas páginas: esta, que apresenta o projeto, e o glossário, que é o produto usado pelos estudantes.

Para quem

Três perfis de estudante, definidos pela equipe, guiam as decisões de tela:

Calouro jovem 17–22 anos

Cresceu usando celular e apps. Quer uma busca rápida, “tipo Google”: digitar e ter a resposta na hora.

Calouro adulto 60+

Tem menos familiaridade com sistemas digitais. Precisa de explicações didáticas, letra maior e navegação simples.

Veterano

Já conhece o básico e usa o glossário para dúvidas pontuais, como uma sigla nova. Valoriza o autocompletar.

Qualidade, além dos requisitos

  • Acessibilidade: busca e navegação por teclado, compatível com leitor de tela e contraste WCAG AA. A auditoria automática (axe-core) não encontrou violações.
  • Testes automatizados: 26 testes, que rodam no CI a cada Pull Request, incluindo a validação de todos os termos.
  • Outros idiomas: ainda não. A tradução está fora do escopo e o preparo da interface para outros idiomas é trabalho futuro.

Fora do escopo por enquanto: login de usuário, favoritos, tradução do conteúdo, edição de termos direto pelo site e aplicativo nativo (o PWA cobre o celular).

Como contribuir

O glossário cresce com a comunidade. Toda sugestão é pública e passa por revisão antes de entrar no site.

Não sei usar Git

  1. Abra o formulário “Adicionar termo” (ou “Corrigir definição”, para um termo que já existe).
  2. Preencha termo, tipo, significado, definição, exemplo de uso e fonte.
  3. Alguém da equipe revisa e publica o termo.

É preciso ter uma conta gratuita no GitHub.

Sei usar Git

  1. Faça um fork do repositório e crie a branch add-termo-<nome>.
  2. Edite frontend/data/termos.json seguindo o modelo abaixo.
  3. Rode npm test e abra um Pull Request para a main.

PR só de dados precisa de 1 aprovação do time.

Como é um termo

{
  "id": "deg",
  "termo": "DEG",
  "tipo": "sigla",
  "significado": "Decanato de Ensino de Graduação",
  "definicao": "Decanato responsável por assuntos relacionados ao ensino de graduação, incluindo acompanhamento acadêmico, currículos e matrícula.",
  "exemplo_uso": "Minha dúvida sobre matrícula foi encaminhada para o DEG.",
  "fonte": "https://deg.unb.br/",
  "campus": "Geral"
}
  • Nenhum termo entra sem fonte: um link oficial ou “conhecimento comum verificado pelo grupo”.
  • tipo é sigla, giria ou expressao; significado (por extenso) é obrigatório só para siglas.
  • campus é Darcy Ribeiro, Ceilândia, Gama, Planaltina ou Geral. Lugares físicos podem ter localizacao e ganham um mapa.
  • O CI confere todo Pull Request: termo fora do padrão ou id repetido não passa.

Regras completas em CONTRIBUTING.md. Viu algo errado num termo? Abra uma issue.

Da tarefa ao site: o caminho de toda mudança

O time usa o GitHub Flow: a main é sempre estável e toda mudança nasce numa branch própria.

  1. IssueA tarefa, com modelo, tamanho (S/M/L/XL) e a milestone da sprint.
  2. Branchfeature/issue-12, criada a partir da main atualizada.
  3. CommitsPequenos e no padrão Conventional Commits.
  4. Pull RequestUsa o modelo e fecha a issue com Closes #12.
  5. Revisão + CIAo menos 1 pessoa aprova (ninguém aprova o próprio) e os testes passam.
  6. Merge e publicaçãoA mudança entra na main e as duas páginas são publicadas.

Por que não Git-Flow completo (develop, release, hotfix)? O time é pequeno e tem poucas branches ao mesmo tempo, então o fluxo mais simples basta. Se isso mudar, a troca será registrada numa ADR.

Mensagens de commit

feat:nova funcionalidade
fix:correção de bug
docs:só documentação
test:testes automatizados
refactor:reorganização sem mudar comportamento
chore:configuração, dependências, infraestrutura

Exemplo: feat(dados): adiciona termo PPAES

Checklist de todo Pull Request

  • Commits no padrão Conventional Commits
  • Termo novo segue o formato e tem fonte
  • Testes adicionados ou atualizados
  • Documentação atualizada, se preciso
  • Uso de IA registrado no AI-USAGE.md
  • CI verde
  • Decisão de arquitetura? Existe uma ADR

Modelos de issue

  • Adicionar termo e Corrigir definição: para qualquer pessoa, sem precisar de Git.
  • Feature: funcionalidade nova, sempre ligada a um requisito (RF/RNF).
  • Bug: comportamento errado, com passos para reproduzir.
  • Tarefa técnica: estudo, configuração ou infraestrutura.

Os modelos de bug, feature e tarefa técnica pedem critério de aceitação, release (R1 ou R2) e tamanho. Os de adicionar e corrigir termo pedem só os campos do termo e a fonte. Cada sprint é uma milestone.

Como a equipe trabalha

  • Scrum com sprints de 2 semanas e um limite de tarefas em andamento emprestado do Kanban.
  • Papéis: Ítalo é o Scrum Master, Jéssyca é a Product Owner e o restante do grupo desenvolve.
  • Reuniões: domingo às 20h (fechar a sprint e planejar a próxima) e sexta às 20h (acompanhar bloqueios). As dailies ficam registradas em docs/scrum/dailies.md.
  • Uma tarefa, uma pessoa, um Pull Request: assim cada entrega é rastreável.
  • Uso de IA é esperado e registrado em AI-USAGE.md. Código ou termo gerado com IA passa pela mesma revisão que qualquer outro.

Arquitetura e decisões

É um site estático, sem servidor nem banco de dados. Os termos ficam num arquivo JSON dentro do próprio repositório, e o navegador faz a busca, os filtros e guarda tudo para funcionar sem internet.

  1. ContribuiçãoPull Request ou issue com um termo.
  2. ValidaçãoO CI confere o formato e a fonte.
  3. termos.jsonO termo entra na main.
  4. PublicaçãoO GitHub Pages publica as duas páginas, com as mesmas pastas do repositório.
  5. ConsultaNo navegador, inclusive offline.

Tecnologias

  • HTML + CSS
  • JavaScript (módulos ES, sem framework)
  • JSON
  • Service Worker + Web App Manifest
  • Leaflet + OpenStreetMap
  • GitHub Actions + node:test
  • GitHub Pages

Decisões de arquitetura (ADRs)

Cada decisão importante tem um registro com contexto, alternativas descartadas e consequências. Todas ainda são propostas, esperando a validação da equipe.

  1. 0001Termos em JSON estáticoSem backend: o Git faz o papel de banco, com histórico e revisão.
  2. 0002Frontend sem frameworkHTML, CSS e JS puros; React ou Vue serão reavaliados na Release 2.
  3. 0003PWA com service worker próprioTermos disponíveis offline desde a primeira visita.
  4. 0004Formato único do termoUm só modelo, validado pela mesma função no site e no CI.
  5. 0005Mapa com Leaflet e OpenStreetMapSó para termos que são lugares físicos.
  6. 0006Contribuição por PR e por issueDois caminhos, ambos no GitHub, sem formulário com servidor.
  7. 0007GitHub Pages e CI com ActionsTestes em todo PR; duas páginas publicadas com HTTPS.
  8. 0008Interface com CSS puroCores em tokens, fontes do sistema, contraste WCAG AA.

Rodar no seu computador

Você só precisa do Node 22 ou mais novo. Não há dependências para instalar.

git clone https://github.com/unb-mds/2026-2-GlossarioUnB.git
cd 2026-2-GlossarioUnB
npm run dev    # glossário em http://localhost:8080/frontend/ e esta página em /sobre/
npm test       # roda os testes e valida todos os termos

Mais detalhes sobre o glossário em frontend/README.md.

Quer consultar um termo? Abra o glossário. Não achou? Sugira pelo formulário no GitHub.
